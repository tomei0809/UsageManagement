# UsageManagement

GitHub Actions、Cloudflare、AWS S3、Supabase、Vercel、Claude、OpenAI、Google Drive など、**複数のサービスの無料枠と利用量を 1 画面で確認・管理する**ための個人向け Web アプリです。

サービスごとに上限・単位・リセット日・確認方法が違うため、一つずつ管理画面を開かないと状況がわかりません。このアプリは使用量を一か所にまとめ、上限に近づいたら気づけるようにします。

> **ステータス:第4段階(超過予測・Discord 通知・無料期間の管理・料金のまとめ・AWS S3)まで実装済み。** 各コレクターは公式ドキュメントに沿って実装し、偽の応答でテストしています。実アカウントで確認済みなのは GitHub Actions のみです(ほかは [docs/services.md](docs/services.md) の「要検証」)。

## 主な機能

### 実装済み(第1段階)
- **サービスと指標の登録・編集・削除**。1つのサービスに複数の指標を持てます(例:Supabase の「DB容量」と「Egress」)。
- **指標ごとの設定**:単位、上限(空欄なら上限なし)、種類(期間内の累積 / その時点の量)、リセット方式(毎月 指定日 / 毎日 / 毎週 指定曜日 / 直近 N 時間のローリング / なし)、リセット基準のタイムゾーン、注意・警告の閾値、「古いデータ」とみなす時間。
- **使用量の手動入力**。入力は毎回履歴として保存されます。確認した日時とメモも残せます。
- **ダッシュボード**:使用率の横棒グラフ、使用量 / 上限、残り、次回リセット日、最終更新日時、取得方法(API取得 / 手動入力 / 推定値)、古いデータの表示。上限到達・警告・注意・古いデータの件数も表示し、深刻な状態のサービスほど上に並びます。
- **警告レベル**:既定は 80% で注意、95% で警告、100% で上限到達。閾値は指標ごとに変えられます。レベルは色だけでなく文字でも表示します。

### 実装済み(第2段階)
- **履歴グラフ**(サービス詳細画面):30日 / 90日の日別、12か月の月別。累積型の指標は「日別の使用量」(前回記録との差分)と「当期の累計」を別々のグラフで表示し、上限線とリセット日を重ねます。容量など「その時点の量」の指標は記録値の推移を表示します。グラフはすべて「表で見る」で表に切り替えられます。
- **月別の区切り**:毎月 N 日にリセットする指標はリセット期間ごと(例:15日〜翌14日)、それ以外は暦月で集計します。日次リセットの指標(Cloudflare の 1日あたりリクエスト数など)は、各日の使用量を月ごとに合計します。
- **要対応リスト**:注意以上の指標をダッシュボードの上部に、深刻度順に並べます。
- **リセット日の管理**:次回リセット日と「あと N 日」を表示します。日付の区切りは指標ごとのリセット基準タイムゾーンで決まります。

### 実装済み(第3段階)
- **公式 API からの自動取得**(Cron で 6 時間ごと)。サービス詳細の「自動取得」で取得方法を選び、トークンなどを入力すると、対応する指標が作られます。
  | 取得方法 | 取得する値 | 必要な認証 |
  |---|---|---|
  | GitHub Actions | 当月の Actions 使用分数、超過料金(USD) | Personal access token |
  | Cloudflare Workers | 当日(UTC)のリクエスト数(アカウント全体) | API トークン(Account Analytics: Read) |
  | OpenAI API | 当月の利用料金(USD) | Admin キー |
  | Google Drive | 使用容量(上限も自動で反映) | OAuth クライアント + リフレッシュトークン |
  | AWS S3 | バケットの使用容量(Standard)・オブジェクト数(1 日 1 回更新) | IAM アクセスキー(CloudWatch 読み取りのみ) |
- **今月の過去分を取得**(GitHub Actions):当月 1 日〜昨日の使用量を 1 日ずつ取得して日別グラフを埋めます。何度実行しても重複しません。
- **今すぐ取得**ボタン、**取得履歴**(成功・失敗とエラー内容)、ダッシュボードの「取得失敗」表示。
- **失敗時の扱い**:一時的なエラー(429 / 5xx / 通信エラー)はその場で 2 回まで再試行します。それでも失敗したら次の再試行までの間隔を 6 → 12 → 24 → 48 時間と延ばし、連続 N 回(既定 5 回)失敗したらそのサービスの定期取得を自動停止します。
- **定期チェックの停止・再開**(下記「[定期チェックを止めたいとき](#定期チェックを止めたいとき)」)。

### 実装済み(第4段階)
- **超過予測**:直近 7 日のペース(期間開始から 7 日未満なら期間開始からのペース)で、期末の使用量と上限に達する日を予測します。容量など「その時点の量」は、上限に達する日を 90 日先まで予測します。予測は保存せず表示のたびに計算し、画面では「予測」ラベルと破線で**実測と区別**して表示します。期末までに上限を超えそうな指標は「超過見込み」として要対応リストに出ます。
- **Discord 通知**(設定画面で Webhook URL を登録):使用率が 注意 → 警告 → 上限到達 と**上がった時だけ**、初めて超過見込みになった時、無料期間の終了 30 日前・7 日前・終了時、自動取得が自動停止した時に送ります。同じ期間内で同じ通知は繰り返しません。Webhook URL は暗号化して保存します。
- **無料期間の終了日**(サービスの編集画面):残り日数を表示し、通知します。「無料期間が終わったら自動取得を止める」も選べます(止めたあとは「再開」で戻せます)。
- **今期の料金**:単位が USD の指標を合計し、指標の上限を予算として使用率・予測を出します。
- **AWS S3 の自動取得**:CloudWatch の日次ストレージメトリクスから使用容量とオブジェクト数を取得します。

### 自動取得にしていないサービス
- Supabase・Vercel・Claude は手動入力で管理します(Supabase・Vercel は将来、自動取得に対応する可能性があります。調査済みの注意点は [docs/services.md](docs/services.md))。

### 無料期間が終わったら(AWS の例)
1. 上限を「無料枠」から「自分の予算」に変える(指標の編集 → 上限値)
2. 料金(単位 USD)の指標を追加し、請求額を記録する(今期の料金に合計されます)
3. 使わないなら自動取得を停止・解除する
- AWS の新しい無料プラン(クレジット制)は、**6 か月またはクレジットを使い切った時点で終了し、有料プランに切り替えないとアカウントが自動で閉じられます**(データは 90 日保持され、その間に切り替えれば復元)。終了日を登録しておくと事前に通知されます。詳細は AWS の公式ページを確認してください。

## 使用量の取得方法

すべてのサービスを自動取得できるわけではないため、データは次の 3 種類を区別して保存・表示します。

| 区分 | 意味 |
|---|---|
| **API取得** | 公式 API から自動取得した値 |
| **手動入力** | 管理画面などを見てユーザーが入力した値 |
| **推定値** | 履歴などから推定した値 |

サービスごとの調査結果(自動取得できる情報と手動入力が必要な情報、必要な認証、未確認事項)は [docs/services.md](docs/services.md) にまとめています。概要は次のとおりです。

| サービス | 自動取得 | 補足 |
|---|---|---|
| GitHub Actions | 可 | 課金 API。無料枠の分数は手動で設定 |
| Cloudflare Workers | 可 | GraphQL Analytics API |
| OpenAI API | 可 | Admin キーが必要。プリペイド残高は手動 |
| Google Drive | 可 | OAuth 2.0 |
| AWS S3 | 一部 | 容量・オブジェクト数は CloudWatch(無料)。リクエスト数・料金は手動 |
| Supabase | 手動 | 自動取得は将来候補 |
| Vercel | 手動 | 自動取得は将来候補 |
| Claude API | 一部 | Admin キーが必要 |
| Claude Pro / Max | 不可 | 公開 API がないため手動 |

**各サービスの無料枠の値はアプリに組み込んでいません。** 無料枠は頻繁に変わるので、上限値は各サービスの公式ページで確認して入力してください。

## 技術構成

| 層 | 技術 | 選んだ理由 |
|---|---|---|
| ホスティング / API | Cloudflare Workers + [Hono](https://hono.dev/) | 常時起動のサーバーが不要で、Free プランで動く。定期実行(Cron Triggers)・秘密情報(Secrets)・DB を同じアカウントで扱える |
| データベース | Cloudflare D1(SQLite)+ Drizzle ORM | Free の容量と書き込み回数に対して、このアプリのデータ量は十分に小さい(下記)。スキーマから型を作れる |
| フロントエンド | React + Vite(SPA)、Workers Static Assets で配信 | 管理画面には SSR も SEO も不要。SPA にすると Worker の CPU 使用も少なく済む |
| グラフ | Recharts(詳細画面でのみ遅延読み込み) | 棒・折れ線・基準線・ツールチップがそろっている。ダッシュボードの初期表示には含めない |
| アクセス保護 | Cloudflare Access(Zero Trust) | ログイン処理を自作しなくてよい。Worker 側でも JWT を検証する |
| テスト | Vitest | 使用率・リセット日の計算を純粋関数にしてテスト |
| 言語 | TypeScript | 計算ロジックと型を Worker と画面で共有 |

### 構成図

```
ブラウザ ──HTTPS──▶ Cloudflare Access ──▶ Worker (Hono)
                                            ├─ /api/*      CRUD・手動入力・ダッシュボード集計
                                            ├─ 静的ファイル  React SPA
                                            └─ scheduled()  Cron(6時間ごと)→ 停止判定 → コレクター
                                                              ├─ GitHub / Cloudflare / OpenAI / Google の公式 API
                                         D1 (SQLite)   services / metrics / snapshots / collector_runs / credentials(暗号化)
```

### データ量の見込み

10 サービス × 平均 3 指標 = 30 指標を 6 時間ごとに記録した場合:

- 約 120 行/日、約 4.4 万行/年、**約 10 MB/年**
- 10 年続けても 100〜150 MB 程度で、D1 Free の 1 DB あたり上限 500 MB に収まります。
- D1 への書き込みは約 150 行/日で、Free の 1 日 10 万行のおよそ 0.15% です。

### データモデル(要点)

管理の単位はサービスではなく**指標(metric)**です。上限・単位・リセット方式は指標に持たせているので、特定のサービスに依存せずに追加できます。

- `services`:サービス名、カテゴリ、管理画面 URL、メモ、自動取得の設定と状態(停止・一時停止・連続失敗数・次の再試行時刻)
- `metrics`:単位、上限、種類(`cumulative` / `gauge`)、リセット方式とリセット日、閾値、鮮度、指標ごとの自動取得オン/オフ
- `snapshots`:値、取得日時、集計期間、取得方法(`api` / `manual` / `estimate`)
- `credentials`:API トークンなど(AES-GCM で暗号化)
- `collector_runs` / `app_settings` / `app_events`:自動取得の実行記録、全体設定、操作ログ

新しいサービスの自動取得を追加するときは、`src/shared/collectors.ts` に定義(入力項目と指標のひな形)を、`src/worker/collectors/` に取得処理を 1 ファイル追加し、`registry.ts` に登録します。

詳しくは [docs/design.md](docs/design.md) を参照してください。

## セットアップ

### 必要なもの
- Node.js 22 以上(開発には 24 を使用)
- Cloudflare アカウント(Free プランで可)

### ローカルで動かす

```bash
npm install
cp .dev.vars.example .dev.vars      # ローカルでは Access の検証をオフにする
# .dev.vars の MASTER_KEY に次の出力を設定(トークンの暗号化鍵)
node -e "console.log(require('crypto').randomBytes(32).toString('base64'))"
npm run db:migrate:local            # ローカルの D1 にテーブルを作る
npm run dev                         # http://localhost:5173
```

ローカルでは「デモ(ローカル確認用)」という取得方法を選べます(`ENABLE_DEMO_COLLECTOR=true`)。外部 API を呼ばずに架空の値を返すので、自動取得・失敗・自動停止の動きをトークンなしで確認できます。定期実行は次の URL を開くと 1 回分を手動で起こせます。

```
http://localhost:5173/cdn-cgi/handler/scheduled?cron=0+*/6+*+*+*
```

> **Windows の場合:** ドライブ文字は大文字(`C:\...`)のパスで実行してください。`c:\...` から `vitest` を実行すると、モジュールが二重に読み込まれてテストが失敗することがあります。
>
> npm 11 の install-scripts 制限で `workerd` / `esbuild` の postinstall が止められた場合は、`npm install-scripts approve esbuild workerd` を実行してから `npm rebuild` を実行してください。

### よく使うコマンド

| コマンド | 内容 |
|---|---|
| `npm run dev` | 開発サーバー(Vite + Workers ランタイム) |
| `npm test` | ユニットテスト |
| `npm run typecheck` | 型チェック |
| `npm run build` | 本番ビルド |
| `npm run deploy` | ビルドして Cloudflare にデプロイ |
| `npm run db:generate` | `src/worker/db/schema.ts` からマイグレーションを生成 |
| `npm run db:migrate:local` / `db:migrate:remote` | マイグレーションを適用 |

### Cloudflare にデプロイする

1. `npx wrangler login`
2. `npx wrangler d1 create usage-management` を実行し、表示された `database_id` を `wrangler.jsonc` に書き込みます。
3. `npm run db:migrate:remote`
4. 暗号化鍵を Secret に登録します(上の `node -e ...` で生成した値を入力)。**この鍵を変えると保存済みのトークンは復号できなくなり、接続設定の入れ直しが必要になります。**
   ```bash
   npx wrangler secret put MASTER_KEY
   ```
5. `npm run deploy`
6. **Cloudflare Access を設定します**(未設定のままだと API は 503 を返し、使えません):
   1. Cloudflare ダッシュボード → Zero Trust → Access → Applications で Self-hosted アプリを作り、デプロイ先のドメイン(`*.workers.dev` またはカスタムドメイン)を対象にします。
   2. ポリシーで自分のメールアドレスだけを許可します。
   3. アプリの **Application Audience (AUD) タグ**とチームドメイン(`<team>.cloudflareaccess.com`)を `wrangler.jsonc` の `vars`(`ACCESS_AUD` と `ACCESS_TEAM_DOMAIN`)に設定し、もう一度デプロイします。

## セキュリティ

- アプリ全体を Cloudflare Access で保護します。Worker も `Cf-Access-Jwt-Assertion` を検証するので、Access を通らない直接アクセスは拒否されます。設定がないときは拒否する側に倒します(fail closed)。
- 自動取得に使う API トークンは、画面から入力すると **AES-256-GCM で暗号化して D1 に保存**します。暗号化鍵 `MASTER_KEY` は Workers Secret に置き、コード・Git・DB には入れません。
- 保存したトークンを API や画面から読み出すことはできません(末尾 4 文字のヒントのみ表示)。変更するときは上書きします。
- 取得エラーのメッセージには、応答本文の先頭 160 文字までしか残しません。
- トークンは各サービスで**読み取り専用かつ最小のスコープ**で発行してください。
- `.dev.vars` と `.env*` は Git に含めません。

## 定期チェックを止めたいとき

停止は 3 段階あり、上の段階で止めると下の段階は実行されません。

| 範囲 | 操作する場所 | 内容 |
|---|---|---|
| アプリ全体 | 設定 → 定期取得「すべて停止」 | すべてのサービスの定期取得を止める |
| サービス | サービス詳細 → 自動取得 | 「停止」(無期限)、「一時停止 1日 / 7日 / 30日」(期限が来たら自動で再開)、「再開」 |
| 指標 | サービス詳細 → 各指標の「この指標を自動取得する」 | その指標だけ値を保存しない。すべての指標をオフにすると API 自体を呼ばない |
| 通知 | 設定 → Discord 通知「停止」 | 通知だけを止める(取得は続く)。停止中に起きたレベル変化は記録だけされ、再開後にまとめて届くことはない |
| 無料期間の終了 | サービスの編集 →「無料期間が終わったら自動取得を止める」 | 終了日を過ぎた最初の定期実行で自動停止(1 回だけ。再開すれば取得を続ける) |

- 連続して失敗したサービスは自動で停止し、理由を画面に表示します(設定 → 失敗時の自動停止 で回数を変更、0 で無効)。
- 停止中でも「今すぐ取得」と手動入力は使えます。
- 停止・再開の操作は `app_events` に記録されます。

アプリ自体を使わなくなったときは、`wrangler.jsonc` の `triggers.crons` を空の配列にしてデプロイしてください。Cloudflare ダッシュボードで Cron Trigger を削除しても同じで、Worker が定期的に起動しなくなります。

## ディレクトリ構成

```
src/
  shared/    Worker と画面で共有する型と純粋関数(使用率・リセット期間・集計・停止判定・コレクター定義)

test/        Vitest
docs/        設計書、サービス別の調査メモ
```
